[문제]
리플렉션을 남용하면 안 되는 이유 2가지(성능, 보안)를 주석으로 설명하세요.

[사용자 작성 코드]
package week11.day5;

public class Problem5 {
    public static void main(String[] args) {
        // TODO
    }
}

[현재 코드 특징]
- 사용자가 직접 작성하는 대신, 개념 이해를 위해 가이드 메모장(.txt)을 통해 개념 설명을 제공받기를 요청하였습니다.

[Better Code]
package week11.day5;

public class Problem5 {
    public static void main(String[] args) {
        /*
         * [리플렉션 남용을 피해야 하는 2가지 주요 이유]
         * 
         * 1. 성능(Performance) 저하:
         *    - 일반적인 메서드 호출은 컴파일 시점에 검증되고 JVM(JIT 컴파일러)의 최적화(메서드 인라이닝 등) 혜택을 받습니다.
         *    - 반면 리플렉션은 실행 시점(런타임)에 클래스 메타정보를 동적으로 해석하고 매칭하므로 성능이 대폭 떨어집니다. (반복문 내부에서의 호출은 치명적)
         * 
         * 2. 보안(Security) 및 캡슐화 위반:
         *    - setAccessible(true)을 통해 private 필드나 메서드에 강제로 접근 및 조작이 가능합니다.
         *    - 이는 객체의 내부 상태를 철저히 감추고 정해진 인터페이스로만 소통하겠다는 객체 지향의 '캡슐화(정보 은닉)' 원칙을 훼손하여 보안 취약 및 디버깅 곤란 문제를 유발합니다.
         */
        System.out.println("리플렉션은 성능과 보안상의 이유로 일반적인 비즈니스 로직에서는 사용을 금하고, 프레임워크 수준에서만 제한적으로 사용해야 합니다.");
    }
}

[기술적 해설]
1. **타입 안전성(Type Safety)의 부재**:
   - 리플렉션 코드는 컴파일러가 타입 체크를 해줄 수 없습니다. 존재하지 않는 메서드나 필드를 호출해도 컴파일 에러가 나지 않고, 프로그램이 실행되다가 중간에 `NoSuchMethodException` 등의 런타임 예외를 터뜨립니다. 이는 협업이나 서비스 유지보수 관점에서 매우 큰 불안정 요인이 됩니다.
2. **JVM 최적화 방해**:
   - 최신 JVM은 자주 호출되는 코드를 분석해 최적화 기계어로 실시간 변경합니다. 리플렉션을 통한 동적 호출은 이 최적화 로직이 분석할 수 없어 항상 느린 기본 인터프리터 경로를 타게 됩니다.
